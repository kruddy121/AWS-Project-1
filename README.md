# Real-Time Security Event Streaming Pipeline

This project is a real-time data streaming pipeline built with AWS and Python. It simulates security-related user activity, streams the events through Amazon Kinesis, processes them with AWS Lambda, stores the processed data in Amazon S3, and allows the data to be queried with Amazon Athena.

## Project Goals

The goal of this project is to build a simple cloud-based real-time security event pipeline that can:

- Generate simulated security events
- Stream events in real time
- Process events automatically
- Store processed security data
- Query stored data using SQL
- Provide a foundation for future security monitoring and analytics

## Architecture

```text
Python Producer
      ↓
Amazon Kinesis Data Streams
      ↓
AWS Lambda
      ↓
Amazon S3
      ↓
Amazon Athena
```

## Data Flow

1. `producer.py` generates simulated security events.
2. Each event is sent to Amazon Kinesis Data Streams.
3. Kinesis triggers the AWS Lambda function.
4. Lambda decodes the incoming Kinesis record from Base64.
5. Lambda converts the event back into JSON.
6. The processed event is stored in Amazon S3.
7. Amazon Athena queries the stored S3 data using SQL.

## AWS Services Used

### Amazon Kinesis Data Streams

Amazon Kinesis receives the security events generated by the Python producer in real time.

### AWS Lambda

AWS Lambda processes incoming Kinesis events. The Lambda function decodes the Kinesis payload, converts it back into JSON, and stores the processed event in Amazon S3.

### Amazon S3

Amazon S3 stores the processed security events.

The current folder structure is:

```text
security-events/
└── YYYY-MM-DD/
    ├── event-HH-MM-SS.json
    ├── event-HH-MM-SS.json
    └── ...
```

### Amazon Athena

Amazon Athena allows SQL queries to be run directly against the security event data stored in S3.

### Amazon CloudWatch

Amazon CloudWatch is used to monitor Lambda execution and view logs for troubleshooting.

### AWS IAM

AWS IAM is used to manage permissions for the AWS CLI user and Lambda execution role.

## Event Data

The Python producer generates simulated security events with fields such as:

```json
{
  "timestamp": "2026-09-30T16:03:22.125401+00:00",
  "user_id": "user_104",
  "ip_address": "192.168.7.83",
  "event_type": "failed_login",
  "device": "Windows",
  "location": "Maryland",
  "risk_level": "medium"
}
```

## Event Types

The producer currently simulates:

- `login_success`
- `logout`
- `failed_login`
- `password_reset`
- `account_locked`

The event types are weighted so that normal activity occurs more often than higher-risk security events.

## Risk Levels

| Event Type | Risk Level |
| --- | --- |
| `login_success` | Low |
| `logout` | Low |
| `failed_login` | Medium |
| `password_reset` | Medium |
| `account_locked` | High |

```bash
python3 -m pip install boto3
```


## Running the Producer

First, verify that AWS CLI authentication is working:

```bash
aws sts get-caller-identity
```

Verify that the AWS region is set to:

```text
us-east-1
```

Check the current region with:

```bash
aws configure get region
```

Then start the producer:

```bash
python3 producer.py
```

The producer generates and sends a new simulated security event approximately every five seconds.

Stop the producer with:

```text
Control + C
```

## Example Athena Queries

### Count Events by Type

```sql
SELECT event_type, COUNT(*) AS total_events
FROM security_events
GROUP BY event_type
ORDER BY total_events DESC;
```

### Count Events by Risk Level

```sql
SELECT risk_level, COUNT(*) AS total_events
FROM security_events
GROUP BY risk_level
ORDER BY total_events DESC;
```

### Find Users With the Most Failed Login Attempts

```sql
SELECT user_id, COUNT(*) AS failed_logins
FROM security_events
WHERE event_type = 'failed_login'
GROUP BY user_id
ORDER BY failed_logins DESC;
```

### Analyze Events by Location

```sql
SELECT location, COUNT(*) AS total_events
FROM security_events
GROUP BY location
ORDER BY total_events DESC;
```

## Security

AWS credentials should never be stored directly in the project files.

Do not include:

- AWS access keys
- AWS secret access keys
- Session tokens
- Passwords
- Private API keys
- `.env` file contents

AWS credentials should remain configured locally through the AWS CLI.

The `.gitignore` file should include:

```gitignore
__pycache__/
*.pyc
.env
.env.*
.venv/
venv/
.DS_Store
*.pem
*.key
```
